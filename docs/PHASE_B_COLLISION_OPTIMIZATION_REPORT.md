# Phase B — Liminal Collision Optimization Report

**Project:** NyxoGame — Unity 6000.6.4f1  
**Date:** 2026-11-09  
**Target:** `Assets/Scripts/Scene1/Scene1OpeningManager.cs`  
**Scope:** Collision-only Phase B. Phase A manager caching was preserved. No collider geometry, models, rendering, video, or project settings were changed.

## 1. Original collision architecture

`BuildLiminalEndingEnvironment` instantiates five imported OBJ models under a generated environment root at (4096, 0, 4096): model_0 door, model_1 shell, and model_2–model_4 terrain/path. The importer metadata for all five assets says `addColliders: 0`; colliders are added by runtime code.

- For each `MeshFilter` below model_0 and models 2–4 with a non-null mesh, the code adds a non-convex `MeshCollider` if that object does not already have one.
- The shell (model_1) is used for rendering/shell visibility and has no generated collider in this method.
- `CreateLiminalBoundary` creates 24 panels, each with a `BoxCollider`. The panel width is 1.2 times the nominal perimeter segment, deliberately overlapping neighboring panels to prevent gaps.
- `TeleportPlayerToLiminalRoadEnd` casts down from above the spawn point and accepts the hit only when it belongs to one of the cached model_2–model_4 terrain roots. It then places the player and enables the existing `CharacterController`.
- Door interaction is based on horizontal distance to the door and the Interact key (prompt threshold 6.5 m); it is not a camera raycast. The door's collider may still be needed to preserve physical blocking/contact behavior, so it has been retained.
- The environment is activated, placement/bounds are computed, boundary panels are created, and the method calls `Physics.SyncTransforms` before returning. The caller immediately teleports the player and performs the terrain ground raycast.

## 2. Implemented change

Removed the first of the two `Physics.SyncTransforms` calls in `BuildLiminalEndingEnvironment`. The remaining call stays after the boundary colliders have been created and before the method returns.

The removed call was followed only by renderer-bounds placement calculations and construction of the boundary panel transforms. There is no physics query, yield, or physics simulation between the two original sync calls. The final sync therefore updates transforms for the terrain/door colliders and all 24 boundary colliders before the caller's ground raycast and subsequent player movement.

The Phase A manager cache is unchanged. No other collision settings or gameplay conditions were modified.

These file sizes do not provide Unity MeshFilter, vertex, triangle, or submesh counts. No large model was instantiated or reimported to obtain those counts. No mesh or mesh-complexity change was made.

## 4. Deliberately unchanged

- **Terrain collision:** All three terrain roots remain collidable. The spawn-ground raycast explicitly filters to these roots, and the player must walk across them. Without exact mesh topology and a collision proxy validated against the walkable route, replacing these colliders could introduce gaps or incorrect slopes.
- **Door collision:** Retained. Proximity/key interaction does not itself prove the collider is unnecessary for blocking or contact behavior.
- **Boundary:** All 24 panels remain. Their overlap margin prevents gaps; deleting panels or reducing overlap without geometric runtime validation could open an escape gap.
- **Shell:** No collider is created by this method; no removal was needed.
- **Other synchronization:** The final sync remains because the boundary has just been created and the caller immediately raycasts for the ground. No physics project setting was changed.

## 5. Expected performance impact and risks

The change removes one physics-transform synchronization pass from the one-time environment construction. Expected benefit is limited to CPU/physics setup work during the transition; no FPS gain was measured, and this is not expected to establish that the collision system was the sustained-FPS bottleneck. Collider counts and runtime mesh complexity are unchanged.

Gameplay risk is low based on the inspected synchronous call order: no physics query or frame yield occurs before the retained final synchronization. Runtime behavior is still unverified. If Unity project code or model-attached behavior is later added between those calls, re-evaluate this assumption.
